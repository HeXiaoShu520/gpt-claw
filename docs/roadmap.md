# gpt-claw 产品路线与验收标准

更新：2026-10-19。本文是产品演进顺序与完成标准的统一入口；具体桌面实现、依赖与已有验收证据见 [混合桌面实施方案](computer-integration.md)，模块职责见 [架构](architecture.md)。

## 产品目标与当前结论

gpt-claw 是本人电脑上的个人助理，专属桌宠负责陪伴、语音、任务呈现和桌面交互，飞书提供另一入口。两者复用同一服务和 Codex 执行内核。

目标体验：本人交代任务后，助理能够组合网页、文件与本地软件完成工作，说明结果并交付产物；遇到不确定状态时说明卡在哪里，本人可以随时取消或接管。

**当前定位：核心功能已有实现，整体验收尚未完成。不能称为完整稳定成品，也没有证据证明桌面成功率、速度或成本全面优于直接使用 Windows-MCP。**

| 范围 | 当前状态 | 尚欠的证据或能力 |
|---|---|---|
| 执行内核 | 已接入原生线程、上下文、审批及中断 | 各入口与模型服务的完整使用链路仍需按场景验收 |
| 桌面感知 | 已实现截图、UIA 控件与混合观察；独立窗口采集已验证 | 常用软件、自绘区域、多显示器与缩放覆盖 |
| 桌面执行 | 已实现元素复核后坐标点击、输入及现有 Win32 动作 | 完整桌宠中的产品工具点击、输入和结果检查 |
| 授权与接管 | 已实现当前轮次授权、撤销、取消与物理输入监听；部分协议及线程启停已验证 | 真实物理接管、竞态与故障场景的完整运行验收 |
| 专属桌宠 | 已接入回复、卡片、语音、目标指示及截图排除代码 | 本轮新增指示与截图排除效果的完整运行验收 |
| 浏览器与文件 | 已有网页操作、会话文件、结果交付与浏览器取消联动 | 端到端任务；上传、下载等网页能力尚待补齐 |
| 多步骤恢复 | 已有任务状态、发件重试；运行中任务中断后不自动重放 | 业务步骤检查点、结果核对与本人确认后的续跑 |
| UIA 原生执行 | 尚未实现 Invoke/Value | 可作为针对常用软件的后续增强，不是基础版完成的必选条件 |

“已实现”仅表示存在对应代码；“已验证”必须附环境、场景和结果。静态检查、独立组件验证和完整运行验收分别记录，不能互相替代。

2026-10-19：普通消息的身份前缀已简化，会话目录和共享状态改为工具按需查询，取消每轮向用户正文追加运行长提示；共享与动作的实际校验仍在服务中执行。这是上下文与体验整理，未完成下文 P0 的完整实机验收。

## 什么叫基础版完成

基础版以明确支持的软件和任务范围交付，不以“能操作所有软件”为完成标准，也不必等待本文全部远期项目实现。

基础版发布需要满足：

1. 在完整 gpt-claw 服务与桌宠中，实际完成约定的点击、输入、等待、指示和产物交付任务。
2. 共享关闭、旧租约、旧元素引用、目标变化、UI 断线均按预期拒绝后续操作；真实接管和取消后的行为有记录。
3. 动作已经发出但结果不明时，先观察核对，不能把超时当作未执行并重复提交。
4. 支持环境、安装方式、失败提示、已知限制和人工恢复方式都能按文档复现。
5. 同一批任务重复执行后，已知严重问题得到修复或从支持范围中明确排除，并保留实际结果。

UIA 原生操作、更多应用 API、事件自动化和跨设备能力属于增强项；不能因为未来还要演进就让基础版无限延期。

## 演进顺序

| 优先级 | 阶段 | 用户能得到什么 | 启动与完成条件 |
|---|---|---|---|
| P0 · 当前 | 可靠性与完整实机验收 | 知道哪些任务可用、失败怎样处理、如何停止 | 先完成下方场景；有完整运行证据后才称为基础版完成 |
| P1 | 常用软件的执行增强 | 支持时直接操作控件，减少坐标与焦点依赖；补齐常用网页任务 | P0 后按实际失败记录选择软件和能力，小范围验收后推广 |
| P2 | 网页、文件、软件的一次完整协作 | 一句话完成资料收集、文件生成、软件检查及交付 | 先完成一个有明确产物的真实流程，再考虑通用抽象 |
| P3 | 任务可见、故障可解释、受控续跑 | 看得到已完成步骤、产物、失败原因；明确核对后继续 | 先有步骤状态与数据迁移，再开放恢复；未知外部结果不得自动重放 |
| P4 · 按需 | 高频流程、事件与陪伴深化 | 常用任务更省事，明确事件到来时主动帮助 | 由真实使用需求触发；默认关闭，明确范围和通知节奏 |

阶段表示依赖关系，不承诺未经测量的工期。P0 后优先解决真实失败，不按功能数量机械推进。

## P0：先完成可复现的实机验收

验收使用独立目录与仅含验收数据的窗口，避免在本人当前文档、网页表单或聊天里试点。环境和证据记录在本工程；本节只定义工作，不表示这些场景已经通过，也不要求现在新增或运行测试套件。

| 场景 | 完成标准 |
|---|---|
| 完整启动与连接 | 服务、桌宠、个人工具均就绪；共享初始关闭；重连状态可解释 |
| 控件观察与回退 | 中文标签可识别；控件缺失或截断明确提示；语义不可用时能使用截图 |
| 点击、输入、等待 | 通过产品实际工具操作验收窗口，中文输入正确，等待命中和超时结果准确 |
| 目标与引用变化 | 窗口移动、切换、关闭以及旧引用均被复核，不能误操作另一个窗口 |
| 接管与停止 | 真实鼠标、键盘及 Ctrl+Alt+Esc 能触发预期停止；后续步骤不再发起；已发出的输入单独说明 |
| 断线与超时 | 共享撤销、桌宠断线及 UIA 卡住后能退出或清理；不会自动重放输入 |
| 截图排除与指示 | 宠物和面板按预期从截图排除，标记指向正确位置；截图前收起标记 |
| 多显示器与缩放 | 至少覆盖实际使用的显示器布局、负坐标与不同 DPI；记录未覆盖环境 |
| 浏览器协调 | 同一任务的网页/桌面调用正常切换；取消阻止排队动作，冲突不会争抢操作 |
| 完成但截图失败 | 能重新观察实际状态，不再次点击提交；“成功”基于实际结果 |

验收记录格式：日期、版本与环境、任务、预期结果、实际结果、人工介入、耗时、可用的模型用量、产物/截图证据、问题及复现步骤。正式结论回填 [实施记录](computer-integration.md#实施记录)，不能只保存在聊天里。

同时选一批常用任务，在相同模型、输入与初始状态下，对照直接使用 Windows-MCP；需要评估截图路线时再加入现有截图模式或 dsh-orb。区分宿主整合收益与底层工具表现，记录成功率、人工介入、耗时和模型用量。小样本只能说明覆盖任务中的结果；没有收益的适配应简化或撤回。

主要涉及：`tools/computer.ts`、`src/services/screen-share.ts`、`src/services/windows-mcp.ts`、`src/desktop/gateway.ts`、`desktop/src/screen_share.py`、`desktop/src/input_monitor.py`。此阶段优先修复缺陷，不扩建框架。

## P1：按实际支持的接口执行

选择 P0 暴露问题最多且日常常用的软件，先补少量有明确收益的能力。

- **Invoke**：控件支持时直接触发按钮动作；返回调用结果后仍检查业务结果。
- **Value**：控件支持、可用且可写时设置字符串值；不把所有编辑器都当作支持 SetValue。
- **网页补齐**：按需求增加上传、下载与文件落盘结果；沿用会话文件目录和交付链路。
- **感知成本**：根据任务选择仅控件、截图或混合观察，检查裁剪、文本数量与模型用量；不默认每一步重复发送最大截图和完整控件树。

UIA 写操作必须与只读观察显式区分，继续经过宿主的当前轮次授权，在执行侧复核窗口、进程和控件身份。优先沿用现有服务和工具入口，不让模型选择两套含义重叠的桌面工具。

回退规则：确认控件不支持且动作尚未发出时，可改用鼠标键盘；一旦动作可能已发出、发生超时或结果不明，先重新观察核对，不直接换另一种方式重复执行。不能把“原生调用没有报错”等同于任务完成。

主要涉及：`integrations/windows-mcp/observer.py` 的采集/能力契约、必要的执行适配、`src/services/windows-mcp.ts`、`tools/computer.ts`、`src/services/browser.ts` 与 `src/tools/builtins.ts`。当前观察进程仍是只读，写能力属于后续设计与实现。

完成标准：在支持控件和不支持控件两类窗口中，分别验证执行与回退；相比现有方式有可记录的成功率、介入次数或效率收益；原授权与取消条件仍成立。

微软接口定义：[Invoke](https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/implementing-the-ui-automation-invoke-control-pattern)、[Value](https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/implementing-the-ui-automation-value-control-pattern)。

## P2：完成一件真实工作

首个样板流程：本人给出网页资料与需求 → 收集信息 → 生成报价表和方案 → 打开本地软件检查 → 桌宠指出待确认项 → 按授权交付结果。

实施顺序：

1. 固定输入、产物与“完成”的判据，每一步都能核对实际输出。
2. 文件/API 适合的数据操作直接处理，网页优先 DOM，桌面按支持情况使用原生控件或坐标；截图用于视觉判断与核验。方法切换仍受目标与授权限制。
3. 遇到缺登录、缺权限、界面变化或外部结果不明时，准确说明已完成和待确认的部分。
4. 样板流程重复可用后，再将确有重复的部分抽成小工具或业务流程；不先造通用工作流引擎。

完成标准：产物内容与用户需求一致，完整流程可复现；中途失败不虚报成功、不重复提交，最终交付有明确结果。应用 API 只按这个流程暴露的需求引入，不承诺覆盖所有软件。

## P3：从能执行走向日常可用

先增加任务与步骤的最小状态记录：任务 ID、轮次、步骤状态、脱敏错误、耗时、产物引用和需核对的外部结果。模型对话继续由 Codex 保存，不复制一套完整聊天或长期记忆。

状态至少区分“尚未执行”“正在执行”“已验证完成”“结果未知”“已中断”。本人确认继续后重新观察，核对产物及外部状态，再选择未完成步骤；不保存永久可用的坐标或元素引用，不直接重放旧模型轮次。

桌宠增加任务进度、产物和失败原因入口。会话历史按原生线程关联，桌面展示历史与模型历史分清来源；不会因为使用同一 ChatGPT 账号就承诺同步到普通云端聊天。

持久化之前补 schema 版本、迁移与备份恢复说明；增加会话/附件保留策略、任务资源上限和无进展提示。对接管、超时和进程退出后的恢复均给出用户可理解的状态。

主要涉及：`src/storage.ts`、`src/app/`、`src/services/jobs.ts`、`src/services/session-files.ts`、`src/desktop/gateway.ts` 与桌宠卡片/聊天界面。完成标准是重启后能解释任务处于哪里，并在核对后继续；不能用“重新发送相同要求”冒充步骤恢复。

## P4：从真实使用中演进

- 高频重复任务：将已经稳定的流程参数化，由本人明确触发；保留确认点和失败出口。
- 明确事件：按需监听指定文件变化或业务事件，先过滤、合并和去重，再决定是否启动模型。
- 专属宠物体验：统一倾听、思考、执行、等待本人和失败状态；本地动画不调用模型，主动模型任务另行授权。
- 其他感知与执行环境：只有自绘控件覆盖率或桌面干扰成为实际瓶颈时，才评估 OCR/视觉定位或独立桌面；不是基础依赖。

事件任务默认关闭；需要定义作用范围、安静时段、通知节流、取消方式和模型用量。保持现有单人、本机范围，跨设备、额外通道和复杂权限体系由后续真实需求决定。

## 维护与取舍

- Codex 继续负责模型循环、原生工具、上下文与原生记忆；不另造执行内核。
- Windows-MCP 固定版本的内部采集接口存在升级成本；升级前核对结构化输出、窗口范围、静态文字、稳定身份、截断及取消清理。不要直接放宽依赖版本。
- 同一业务入口复用浏览器、授权和文件服务；出现第二个真实复用方后再考虑独立共享包。
- 输入接管属于尽力而为，进程内互斥也不能控制其他软件的自动化进程；不把它们写成绝对安全保证。
- 每次变更更新本路线的状态和对应实施记录。未验收项保持未验收；没有对照数据时不承诺更快、更省或成功率更高。

## 下一次工作的具体范围

从 P0 开始：准备独立验收窗口与目录，运行完整服务和专属桌宠，完成产品工具的中文输入、等待、指示、截图排除和真实接管；修复实际缺陷并记录结果。P0 没有结论前，不同时推进原生执行、视觉模型、任务引擎和更多平台。
